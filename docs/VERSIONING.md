# 版本命名规范

> **一句话**：有没有「功能更新」决定动哪一位 —— **有功能更新进次版本（+0.1.0），
> 没有就进补丁版本（+0.0.1）**；本仓的版本号是**仓库发布号**，
> 只在 [CHANGELOG.md](../CHANGELOG.md) 的版本标题里维护。

适用范围：本仓的**仓库发布号** —— [CHANGELOG.md](../CHANGELOG.md) 的版本标题、
Release 说明文件名、发版 tag，三处**必须一致**。

本仓**有**构建产物（`dist/`），但 **`dist/` 不入库**（`.gitignore` 已排除），
所以版本号仍然**只手工维护在一处**。

---

## 1. 三段式与进位规则

版本号是三段式：`主版本.次版本.补丁版本`（如 `0.1.0`）。

| 这次发版包含…… | 动哪位 | 写法 | 例子 |
|---|---|---|---|
| **没有功能更新** —— 只修 bug、改文案 / 样式、改文档、调参数 | **补丁版本 +0.0.1** | `x.y.z` → `x.y.z+1` | `0.1.0` → `0.1.1` |
| **有功能更新** —— 新增了使用者可感知的新能力（新增页面 / 新增 CGI 能力 / 现有行为变了），或现有能力的行为变了 | **次版本 +0.1.0**，补丁归零 | `x.y.z` → `x.y+1.0` | `0.1.0` → `0.2.0` |
| **破坏性变更** —— 现有用法不再成立（请求 / 响应 JSON 形状变了、CGI 的 action 变了、目录结构变了） | **次版本 +0.1.0**，并在 [CHANGELOG.md](../CHANGELOG.md) 的版本段落里**显式标注** | `x.y.z` → `x.y+1.0` | `0.1.0` → `0.2.0` |

进位是**连锁**的：次版本进位时补丁必然归零（`0.1.0` 的下一次功能更新是 `0.2.0`，
不是 `0.2.1` 也不是 `0.1.2`）。

## 2. 判断判据

判断口诀：**写这一版的 Release 说明时，会不会出现「新增 / 变更 / 移除了某能力」
这样的句子？**

- 会 → **有功能更新** → `+0.1.0`；
- 不会，全文只有「修复 / 调整 / 优化」→ **没有功能更新** → `+0.0.1`。

几个边界情况：

| 情况 | 算不算功能更新 | 理由 |
|---|---|---|
| 修一个「本该生效却没生效」的 bug | ❌ `+0.0.1` | 行为回到了它本来该有的样子，不是新行为 |
| 删掉某项能力 / 某个页面 / 某个 CGI | ✅ `+0.1.0` | 能力清单变了，使用者可感知的减法也是更新 |
| 只改文档、只改措辞、只动与产物无关的构建配置 | ❌ 连补丁版本都不给 | 见 §5：这类改动**根本不动版本号** |
| 改了 `src/` 里的页面逻辑（哪怕只是修一个交互细节） | ✅ `+0.1.0` | 产物变了，使用者拿到的东西变了 |
| 破坏现有用法（请求 / 响应形状变了、action 改名了） | ✅ `+0.1.0` + CHANGELOG 显式标注 | 见 §1 第三行 |

拿不准时问一句：**这次发版，使用者拿到的东西比上次多了还是少了？**
多了 → `+0.1.0`；没多没少 → `+0.0.1`。

> 本仓的「能力清单」就是根 [README.md](../README.md) 的「功能」表与
> [docs/ARCHITECTURE.md](ARCHITECTURE.md) 的「10 个数据通道表」：
> 多了一个页面 / 多了一条通道 / 多了一个 CGI → `+0.1.0`；
> 只是某页的文案或样式变了 → `+0.0.1`。

## 3. 版本号在哪维护

**只有一处：[CHANGELOG.md](../CHANGELOG.md) 的版本标题**（形如 `## [0.1.0] — 2026-10-20`）。

本仓**有构建产物，但产物不入库**，因此：

- 版本号**不从 `dist/` 里读**，也没有第二个「真正的版本号」藏在别处 ——
  改版本号 = 改 [CHANGELOG.md](../CHANGELOG.md) 的段标题；
- 构建产物里也**读不出**版本号：Vite 产出的 `index-<hash>.js` / `index-<hash>.css`
  带的是**内容 hash**，不是版本号 —— 想确认「部署上去的是第几版」，
  看 [CHANGELOG.md](../CHANGELOG.md) 或部署记录，不要去产物里找；
- 由版本号派生出两处**必须与标题一致**的引用：
  - Release 说明文件名 [docs/release-notes/v0.1.0.md](release-notes/v0.1.0.md)
    （格式正本见 [docs/release-notes/README.md](release-notes/README.md)）；
  - 发版 tag（`v0.1.0` 形式，tag 名 = 版本号）。

### ⚠️ `package.json` 里的 `version` 字段**不是**本仓的版本号

`package.json` 有 `"version": "1.0.0"`（2026-10-20 建仓时的值），
而本仓的发布号是 `0.1.0` —— **两者对不上，而且永远对不上**。

- 本仓 `"private": true`，**根本不发包**，那个字段不参与任何发布流程；
- 它也**从不与 CHANGELOG 同步**；
- **别拿它当版本号**，也别为了「让它们一致」去改它 —— 改了没有意义，
  反而会让人误以为存在第二个版本号真源。

> 需要「当前是第几版」时，唯一答案在 [CHANGELOG.md](../CHANGELOG.md) 的版本标题。

## 5. 什么时候不动版本号

**只改文档、只修拼写、只动与产物无关的配置 → 不动版本号。**

这类改动只在 [CHANGELOG.md](../CHANGELOG.md) 顶部的 `## [未发布]` 段**追加一条**，
**不新开版本段落**。理由：版本号是给使用者看的「这次拿到了什么」的标记，
文档措辞与流水线的修正不改变使用者拿到的东西。

`[未发布]` 段攒够了再发版：把段标题改成 `## [x.y.z] — <发版日期>`，
并补一份同名的 Release 说明。

> 本仓的例外提醒：**改了 `src/` 或 `deploy/` 就是改了产物** —— 那已经算功能更新，
> 按 §1 走 `+0.1.0` / `+0.0.1`，**不要**按「只是改了点代码」放进 `[未发布]` 了事。

## 6. 与 CHANGELOG 的关系

| 主题 | 唯一正本 | 其余位置怎么写 |
|---|---|---|
| **版本号本身**（当前是哪个版本、历史上有哪些版本） | [CHANGELOG.md](../CHANGELOG.md) 的版本标题 | 只留一句话 + 链接，不复制版本历史 |
| **进位规则**（下一次该动哪一位） | 本篇 §1 与 §2 | 只留一句话 + 链接，不抄表格全文 |

两处都写全文，迟早各改各的 —— 单一正本原则见 [docs/DOC-RULES.md](DOC-RULES.md)。
