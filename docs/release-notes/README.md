# release-notes/

> **一句话**：放**面向用户**的 Release 说明，文件名 = 版本号 ——
> 一份文件讲清「这一版用户能拿到什么」，格式规范就在本篇。

```
docs/release-notes/v0.2.0.md
```

## 为什么要单独放一份

`CHANGELOG.md` 是**开发者记录**：症状 / 根因 / 改法 / 验证结果 / 部署细节 / 待修缺陷清单。
Release 说明是**给用户看的**，要短、写成清单、只讲「我现在能拿到什么」。
两者受众不同，不能一份两用。

**特别注意**：本仓的 `CHANGELOG.md` 里有一整段「修复（待修）」——
那些是**还没修**的缺陷，**绝不能**出现在 Release 说明里。
Release 说明只写用户**已经能拿到**的东西。

## 形状

**清单，不是文章。** 开头一句加粗说清这版是什么，
`## 本版内容` 下按分区一行一条，最后是固定尾巴。

```markdown
**控制台可以读写防火墙配置了；软件包管理、固件刷写与 ShellCrash 设置页也都能用了。**

## 本版内容

**配置**

- 调整 防火墙配置 —— 配置页 → 防火墙；区域、端口转发、出站规则、流量卸载都能改并应用。
- 调整 无线配置 —— 配置页 → 无线；SSID、射频、信道与发射功率可改。

**运维**

- 新增 软件包 —— 配置页 → 软件包；apk 已装列表、仓库检索、安装与卸载、索引更新与全量升级。
- 新增 固件与备份 —— 配置页 → 固件；上传固件并刷写，配置备份与恢复。

---

需要路由器 root 密码，以 root 身份访问 <https://<路由器IP>/modern/>（多数路由器的地址是 `10.0.0.1`）。
部署步骤见 [README](../../README.md)。

---

> 风险提示：本控制台以 root 权限在路由器上执行命令，刷写固件、恢复出厂、改密码、
> 重启属于不可逆或高风险操作；请先做配置备份，并确认固件来源可靠。
> 使用前请阅读 [免责声明](../../README.md#免责声明)。
```

结尾那两行加风险提示段是**固定尾巴**，每版照抄不动。风险提示段**逐字粘贴、不随版本改写**
（法律留痕：持续提示、提示在先），它是固定尾巴的一部分，**不算重复内容**。

### 一条怎么写

```
新增 / 调整 / 修复 / 优化 + 功能名 —— 入口；一句话功能
```

- **动词只有四个**：新增（以前没有）、调整（行为、默认值、位置变了）、
  修复（以前不对，**含底层与实现层**）、优化（用户能感知的更快 / 更小 / 更顺）；
  另有「移除」用于删功能。都写全称 —— 单字「修」读着不像词。
- **功能名照抄界面上的名字**（页面标题、菜单项、按钮），不加引号书名号，也不另起一个说法。
- **入口**写用户点得到的位置：「配置页 → 防火墙」「系统 → 重启」；不需要找入口的
  （列表里一眼能看见），改写场景（「客户端列表」）。
- **功能**一句说完，写用户拿到什么。不写怎么用、不写为什么、不写「点一下就会…」。
- 说人话。「rpcd ACL」「UCI 事务」「ubus」这类只对开发者有意义的词别写；
  真要交代限制，写用户看得见的后果（「改完要重启网络才生效」）。
- 一行一条。两句才说得清 → 拆成两条，或者这条本来就该留在 CHANGELOG。

## 底层与内部改动：算「修复」，而且要拆开写

这条是给「用户看不出区别、但代码确实改了」的改动定的。**它们也算本版内容，
必须写；而且要一条一条拆开，不许打包成一句。**

| 改了什么 | 动词 | 一行怎么写 |
|---|---|---|
| 底层缺陷（竞态、越界、时序、编码、量纲） | 修复 | 写「以前会怎样」的后果，不写根因 |
| 重构 / 拆文件 / 收敛依赖（行为零变更） | 修复 | `修复 代码拆分 —— 哪几处拆开，行为零变更` |
| 删死代码、删悬空注释、清无用资源 | 修复 | `修复 死代码 —— 删了哪几处，行为零变更` |
| 日志 / 文案 / 注释口径纠错 | 修复 | 写纠了什么口径，不写讨论过程 |
| 仓库结构（文档正本新增、内部记录移出公开仓库） | 调整 | `调整 仓库 —— …`；用户不可见的也照写 |
| 用户能感知的更快 / 更小 / 更顺 | 优化 | 写「快在哪」，并给数字（体积、帧、次数） |

**禁止写法**：

- ❌ `优化 代码整理 —— 大文件按职责拆分、包依赖方向收敛，行为零变更`
  —— 三个改动压成一句，对不上 CHANGELOG，下个版本没人知道拆了哪些文件；
- ❌ `修复 稳定性 —— 中危 3 条、低危 10 条全部清零，细目见 CHANGELOG`
  —— 「细目见 CHANGELOG」等于没写，用户和我们自己都不会去翻；
- ✅ 拆成 4~6 行，每行一个对象，行尾该标「行为零变更」的就标。

一句话记法：**凡是在 `git diff` 里出现过的东西，说明里都要有一行**。
写不长不是本事，漏了才是问题 —— 篇幅红线排在覆盖率之后。

## 覆盖率红线

**凡本版改过的东西，必须全部出现在 Release 说明里**，动词四选一（新增 / 调整 /
修复 / 优化），一行一条。没有例外：

- 代码审查的发现与修复 → 并进「修复」分组，一行写「修了什么 + 用户可见的后果」
- 性能优化 → 并进「优化」分组；同类多项可归并成一行，但要列出对象
- 纯重构（行为零变更）→ 并进「修复」分组，**按对象拆成多行**
- 文档 / 法律类（免责声明、第三方声明等）→ 并进「界面」或对应分组，照写

写完拿 CHANGELOG 对应段落逐条对：**CHANGELOG 里的每一处用户可感知改动，
Release 说明里都得能找到对应行**。性能与审查类不另开长段落叙事 ——
那段叙事留在 CHANGELOG，Release 说明只要一行短句。

### 篇幅

- 覆盖率红线优先于篇幅：先保证**一条不漏**，再谈合并。
- 分组按界面分区走（概览 / 配置 / 运维 / 代理），不按轻重排。
- 合并手法：同分区的界面打磨（间距、对齐、动画）并成一行；
  性能同类项归并成一行但列出对象；审查修复写用户可见后果，不写根因长文。

## 别写这些

| 别写 | 为什么 |
|---|---|
| 第二人称叙述（「点一下就…」「你可以在…里改」「想换的话…」） | 用户要的是有什么，不是操作步骤；步骤归 README |
| 「原来是这样，所以现在…」的原因与取舍 | 解释属于 CHANGELOG |
| 实现原理、取数口径、字段来源 | 同上 |
| 开关默认开还是关、改完要不要重启 | 通用信息，不随版本变 |
| 「之前是什么样」的对比 | 只有修复条目允许一句症状（「取不到数据」），其余不写 |
| 「本版没有破坏性变更，直接覆盖安装」 | 没变更就不用声明；**有**的时候才必须写 |
| 凑数的「注意」区块 | 见下 |

## 「注意」区块：能不写就不写

只在**用户不知道就会出问题**时才写，最多一两条：

- ✅ **有破坏性变更** —— 部署路径变了、配置格式不兼容、会话要重新登录。**必须写**。
- ✅ **已知的、会被当成新 bug 的问题** —— 如实写一条，免得被重复报。
- ❌ 每版都一样的操作提醒、性能说明 —— 不写。风险提示**例外**：
  每版说明末尾固定附风险提示段（按本篇模板逐字粘贴），属固定尾巴，不算重复内容。

## 版本号从哪来

版本号规则（**正本在根 [../../CHANGELOG.md](../../CHANGELOG.md) 头部**）：
**有功能更新进次版本（+0.1.0）；没有功能更新进补丁版本（+0.0.1）。**

## 改已经发出去的说明

Release 说明跟着 tag 一起进仓库，可回溯、可 review。
改完文案直接重跑一次发布流程覆盖线上的那份即可。

> 注意：`docs/**` 在多数 CI 的 `paths-ignore` 里 —— 改说明文件本身不会触发构建，
> 但**打 tag 一定会触发 Release 工作流**（tag 事件不受 `paths-ignore` 影响）。
